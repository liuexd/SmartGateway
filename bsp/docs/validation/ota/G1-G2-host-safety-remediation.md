## G1 使用边界

- 旧的 `--allow-rw-snapshot` 选项及 `EMMC_DEV`、`PROC_MOUNTS` 等生产环境覆盖不再支持；无法确定块设备身份、设备或分区缺失、几何不匹配、源设备非只读、存在 eMMC 的 rw 挂载时，full 拒绝。
- 脚本依赖目标恢复环境已有 Python 3、Linux sysfs 和 mountinfo；未确认板端恢复环境具备 Python 3。缺少依赖时失败，不自动安装。
- 备份目标必须是父目录已存在、目标本身不存在的新目录，且只能使用可证明不依赖 eMMC 的块存储。tmpfs、NFS、overlay、无法追溯底层的设备等暂时拒绝，避免猜测。
- 固定基线为 mmcblk1 / 7,634,944 sectors、p1/p2/p3 的已记录 start/size；必要的 boot0/boot1 各 4 MiB 缺失时也拒绝。只适用于匹配此几何的设备。
- full 要求外部恢复环境预先将源整盘、各分区及 boot 区设为内核块只读，并且所有受保护设备无 rw 挂载；不提供自动切换只读的命令。本次并未在板上设置只读。
- 输出包括 pre-p1、p1/p2/p3、尾部、boot0/boot1 及 SHA256SUMS；每项复制后做一次目的文件回读校验。metadata 仅保存 pre-p1，不能当作完整备份。新脚本暂不导出 `fw_printenv` 或 `sfdisk` 文本；必须在恢复流程中另行取得和核对这些信息。SHA256 只证明已读到的数据与目标文件一致，不证明被读设备没有并发变化或备份可恢复。
- 不提供 `conv=noerror` 的填零容错；出错即失败，已经生成的目录标识为不完整，不能用于恢复。验证独立恢复、跨介质备份、保存设备唯一数据与实际恢复仍是 G1 门槛。

## G2 安全行为

`sgw_bootctl confirm` 和 Watchdog 自动确认都依赖 `ab_verify_system_health`。现阶段该函数在部分原有检查之后仍明确返回“可信系统和业务健康服务未实现”，因此**不会确认任何候选槽**。在任何部署之前，必须实现并审核可信健康服务，包括 Supervisor 身份/状态、Gateway 本地业务链、必需设备、DATA 和版本/启动身份，并按需求冻结稳定观察窗口。现有测试通过表示拒绝路径有效，不代表正向确认流程完成。

`stage` 同样必须证明真实根设备。根设备检查只接受根挂载设备与预定义 p1/p2 块设备号一致的直接映射；复杂映射或不支持的 root 参数拒绝。测试参数可替代部分输入，仅用于主机测试；生产权限/配置边界还必须在健康服务集成时彻底审计。环境读取出现任何诊断信息时也拒绝，以防 fw_printenv 因 CRC 损坏返回编译时默认值并退出 0。

Watchdog 模拟中的“健康”是模拟服务；由于根设备和完整健康不可证明，本次预期是试启动不确认并停止喂狗。**不能部署当前 Watchdog 自动确认流程**：真实 watchdog 驱动、超时及复位均未验证，且不完整健康服务会导致反复试启动和回滚。
