## 备份工具实际行为

板端脚本由 `bsp/tools/g1_emmc_backup_verify.sh` 和同目录的 `g1_emmc_backup_verify.py` 共同组成，要求 Python 3、真实 sysfs/mountinfo 设备身份、匹配的全部分区几何，以及可以证明不在 eMMC 上的本地块设备备份目标。`full` 模式还要求 eMMC 及各源设备的内核块设备只读标志为 1，并拒绝发现 eMMC 有读写挂载的情形。

完整备份是**分段文件**，不是自动生成 `mmcblk1.raw`：

| 顺序 | 文件 | 内容 |
|---|---|---|
| 1 | `emmc-reserved-pre-p1.bin` | user area 起始至 p1 之前 |
| 2 | `emmc-p1.img`、`emmc-p2.img`、`emmc-p3.img` | 三个分区，按当前基线的物理顺序 |
| 3 | `emmc-tail.img` | p3 结束至 user area 末尾 |
| 单独 | `emmc-boot0.img`、`emmc-boot1.img` | eMMC 两个硬件启动区 |

工具逐文件读取、写入、`fsync` 并回读比对 SHA-256；全部成功后才写 `SHA256SUMS`。备份完成后，主机可运行 `python3 bsp/tools/g1_verify_segments.py <备份目录>` 只读复核七个分段、校验清单、MBR 基线及合并后的 user area 摘要；这一工具目前仅通过合成文件测试，尚未用于真实板端备份。user area 分段合计 3,909,091,328 字节，另有两个各 4,194,304 字节的 boot 区，至少需约 3.65 GiB 可用空间并预留余量。脚本不会自动导出 `sfdisk` 报告，也不会验证一个整盘 `mmcblk1.raw`。备份完成后应在备份存储上独立核对清单和文件长度；失败产生的目录必须标记不完整，不能当作有效备份。

**限制：** 当前脚本拒绝 tmpfs、未知设备、网络文件系统及不能证明底层设备身份的 FUSE 挂载。不能为了使用 exFAT U 盘而绕过此检查；也不能把运行中的 p2 只读复制称为离线一致备份。脚本采集当前挂载命名空间，恢复环境必须控制其他进程及挂载命名空间，并在备份期间保护源设备不被修改。

## 后续验收次序

1. 确认串口及独立启动路径；如果使用网络内存启动，先评审内核、DTB、initramfs、内存地址、下载服务及回退方法，取得操作授权后记录从上电到内存 shell 的完整串口日志。尚不能假定 U-Boot 支持从 U 盘直接启动。
2. 在恢复环境核验根文件系统确实来自 RAM/外部介质，确认 eMMC 未被读写挂载；仅在确认正确设备后设置和核验内核只读状态。再次核验设备 major:minor、父子关系、几何和目标空闲空间。
3. 先解决备份目标：使用脚本能安全识别的外部本地块设备和支持的文件系统；或者使用正在准备的 SSH 备份通道：恢复端 `g1_stream_segment.py` 每次只读一个固定分段，严格校验源设备及只读状态；主机端 `g1_receive_segments.py` 使用固定主机密钥校验、逐段校验与回读，并在全部通过后验证 MBR 和清单。当前仅通过合成数据与本机 SSH 回环测试，真实恢复系统和目标端尚未联调，不能据此放行真实备份。现有 exFAT U 盘及本地备份脚本的组合尚未验证可用。
4. 执行离线全量分段备份，保留原始输出、源身份、各文件长度和独立的 SHA-256 校验结果。boot0、boot1 要作为独立硬件区域保存，不能把它们与 user area 直接拼在一起。
5. 在隔离镜像或备用设备上验证 user area 分段重组、分区表和内容；这只能证明备份重组正确。真正的板端恢复能力还须经单独授权，使用经过审核的写回方案在合适的备用目标上完成并验证启动，不得为了验收冒险覆盖当前 p2。
