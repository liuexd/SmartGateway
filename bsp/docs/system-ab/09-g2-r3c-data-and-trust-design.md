# G2-R3C：共享 DATA 与可信事务设计决策草案

状态：DESIGN / PARTIAL HOST-TESTED；不是部署方案或板端操作授权。记录日期：2026-11-17。G2-R3C **HOST-ACCEPTED = BLOCKED**。

## 1. 边界和需要先冻结的决策

当前 `/opt/smartgateway` 属于 p2 RootFS，不证明跨槽共享；p1、p3、尾部与环境区用途未完全核实。共享 DATA 应是独立于两套系统槽的文件系统，并由两槽共同挂载到一致的受保护位置；具体路径、硬件区域、UUID 与分区映射尚未批准。p3 只是待核实的候选，不能格式化或预先写死。

产品应建立受保护的布局策略，包含板型、块设备稳定身份、允许的设备及其父磁盘/扇区范围、系统槽排除范围、文件系统类型、schema 版本、挂载点和最小可用空间；策略发布、变更和授权方式尚待设计。major:minor 是本次启动的交叉校验，不是可长期信任的硬件身份，设备节点或文件系统 UUID 也可能被替换。不能由普通调用者或测试变量指定一个目录就放行。

按建议目录角色划分：

```text
DATA/
  system-ota/        # 系统事务与健康证据，受信升级服务管理
  app/               # 现有 releases/current/state/last_operation
  coordination/      # 跨系统/应用 OTA 的共同排他锁与事务协调
  logs/              # 有限保留与空间预算，不能耗尽确认所需空间
```

这是逻辑设计，不是已创建的实际目录。schema 文件 `.sgw-data-schema`、值 `schema=1\n` 是本轮测试用的**候选格式**，尚未完成产品 schema、迁移与权限评审；不能部署或写入板端。未来还需证明真实文件系统可写和持久化，而不能仅凭权限位或 `statvfs`。

## 2. DATA 与应用事务的最小集成设计

1. 在可信根拥有的配置和目录下核实源块设备、mountinfo、挂载实际设备、文件系统根、rw 状态、空间和 schema。拒绝 tmpfs、根分区、设备不符、bind 子目录、重复挂载、缺失和只读。还须排除**所有**系统槽及与它们重叠的扇区；当前增量实现尚未完成此布局级验证。
2. 维护向后兼容的 schema：确认前不得执行使 last-good 无法读取的不可逆迁移；如不可避免，设计版本化副本、迁移事务、回滚及恢复，且旧系统必须明确拒绝不兼容数据。
3. 系统 OTA 与应用 OTA 保留独立状态机。受信协调器在一次系统确认决策全过程持有共同锁，检查应用 OTA `ota_state.json`、`current` 和 `last_operation.json`；检查结束立即释放的共享快照不能消除后续 TOCTOU，不足以授权确认。
4. 使用现有应用 OTA 原子状态/操作日志和锁机制；损坏、未完成、锁忙、无锁文件、目录不可信全部拒绝。互斥锁只约束遵守该锁的进程，需证明每个写入入口都参与协调。
5. 实际候选槽、last-good、DATA 的状态必须在写确认前重读；mount namespace、热插拔、路径替换、设备重映射、文件系统写入中断和持久化回读都需要端到端验证。

## 3. 事务与确认链的信任来源

受信系统升级者验证包签名、板型、镜像摘要和目标范围后，以操作系统随机源生成不可预测 ID；受保护、带崩溃恢复语义的事务记录绑定包/镜像摘要、目标槽、last-good、布局版本和阶段。写入成功并读回校验后才能提交 pending。启动后，受信健康服务重新验证实际根设备、U-Boot 状态、boot_id、bootcount、DATA、Supervisor、完整 Gateway 业务和其他必需设备；稳定观察的每个采样与这次启动关联。

最终确认必须在统一锁和受信进程权限下重读、验证事务、状态和健康证据，防重放；成功只能在持久化及回读成功后报告。旧 boot_id、过期证据、镜像或槽位不一致、事务不存在、重复或冲突确认、存储失败均拒绝或有明确安全幂等策略。单个内存字段比较、用户提供的摘要、随机 ID 本身、签名验证的布尔值或没有持久写入凭证都不证明来源可信。

本轮 `r3c_binding_matches` 只比较受调用方提供的字段及单调时间新鲜度；**不会**认证输入、生成交易 ID、校验镜像、处理重启、记录持久化、持锁、抗重放或确认。它未连接 `sgw_bootctl`，不能用于声称 N09 成功。

## 4. Gateway 业务路径待决策

已有无副作用组件查询可验证解析器和运行中结构，但没有走完整接入、队列和北向转发；历史 OTA L2 会向上游发送测试节点数据，不适用于不污染生产业务的检查。

需要审查并实现从真实业务入口到实际转发工作线程的可关联、可过期证据，证明队列和处理线程在本次启动中前进，同时不产生正式节点、统计或业务消息。候选做法包括在现有业务线程中增加受控、只在本地终止的测试标记，或者对真实业务消息做被动关联；两者各有边界：本地终止不能证明远端已接收，被动观察在无流量时只能返回 UNKNOWN。若要求证明远端接收，必须另有服务端支持的无副作用确认，并明确外网故障与本地系统故障的策略。

必须覆盖业务线程停滞、正常 PID、等待超时、过期证据、进程替换、并发和负载；不能用另起一个固定 OK 的线程冒充业务路径。当前没有完成该实现。

## 5. 进一步关闭 HOST-ACCEPTED 的顺序

1. 冻结 DATA 授权与布局策略，提供隔离块设备/挂载环境，验证真实 mount、schema、可写和跨槽切换及所有系统槽排除。
2. 将受信系统包验证、事务随机生成、持久记录、镜像读回、统一协调和一致确认写入实现为真实生产链；定义授权、生命周期、单调时钟及崩溃/掉电恢复。
3. 完成 Gateway 无副作用业务通道、可信设备/传感器心跳和策略接入；将现有字段比较、稳定观察和数据检查接入生产决策，在持锁下避免竞态。
4. 在隔离后端执行 N09 正常确认，以及 N10 重放、失败、崩溃、过期和持久化失败；记录真实调用链。全部必需拒绝、回归和 ARM 检查通过后再审查 HOST-ACCEPTED。G1/G2 板端仍需独立恢复、真实启动、bootcount 与 Watchdog 证据。
