# G1–G6：A/B OTA 与 Linux 裁剪实施规划

状态：DESIGN；尚未执行本规划的板端阶段。
日期：2026-11-13（Asia/Shanghai）。
基线：U-Boot 2017.03 / Linux 4.9.88 / Buildroot 2020.02 / SWUpdate 2019.11.0。
事实、来源和缺口见 [前置条件与证据](01-prerequisites-and-evidence.md)。本文的参数是设计建议或待冻结指标，不是测试结果。

## 1. 总体路线与阶段依赖

目标是可复现、可恢复、可证明掉电收敛的 Kernel + DTB + RootFS 双槽系统，同时保留应用 OTA 和 Supervisor。第一轮不升级 U-Boot 本体、不同时升级内核主版本和工具链。

```text
G0 既有恢复门槛（当前未通过）
        ↑ 由 G1 收敛证据并验收
G1 恢复与布局事实 → G2 基线复现 → G3 渐进裁剪与容量冻结
                                        ↓
G6 故障验收与交付 ← G5 包/写入/健康集成 ← G4 启动状态与回退
```

G2 的源码整理、编译和 G3 的离线分析可与 G1 并行；这不是板端写入许可。G3 的最终容量和功能结论需要 G2 的基线结果，G4 的板端实现依赖 G1/G0 与 G3，G5 不得越过 G4。

| 阶段 | 核心产物 | 进入下一阶段的硬门槛 | 当前状态 |
|---|---|---|---|
| G1 | 证据矩阵、恢复包清单、备份/恢复报告、路线决策 | G0 恢复和空间用途全部闭合 | BLOCKED：缺恢复/用途/后端证据 |
| G2 | 锁定源码/工具链/配置、基线镜像与构建清单 | 可重复构建；独立安全启动路径下功能基线通过 | PLAN：可先开展主机工作 |
| G3 | 裁剪配置差异、依赖矩阵、槽位/DATA 预算、布局提案 | 镜像适配最小槽；必要功能及增长预算满足 | PLAN |
| G4 | 槽位映射、持久启动状态、bootcount/回退实现与验证 | 加载失败/启动超时/断电后的有限次回退成立 | PLAN |
| G5 | 受信更新包、writer、互斥、系统健康确认 | 双向升级、拒绝路径、健康确认和业务恢复通过 | PLAN |
| G6 | 实际断电矩阵、回归/恢复证据、发布与运维说明 | 必需项全通过，限制明确，无未解释启动状态 | PLAN |

每阶段报告分别记录 DESIGN、IMPLEMENTED、HOST-TESTED、BOARD-TESTED 与 BLOCKED；不能用“编译成功”填“板端通过”。历史 Supervisor 的 G4a/G4b 是应用服务子目标，和本文 G4 无关。

## 2. 全阶段共同约束

1. **保护 p2。** 它当前承载唯一已知工作根和 /boot。不得在线缩容、移动、格式化、覆盖或用整盘镜像间接覆盖。即使未来启动到候选槽，原 p2 仍是 last-good 时也不能写。只有另有已确认系统、恢复链已验证且专门迁移步骤通过后，才评审将旧 p2 纳入轮转；本规划不是该写入动作的授权。
2. **只写经过批准的非活动槽。** 目标由板级布局映射确定，不从未经验证的包路径、网络参数或字符串猜测。检查 active、last-good、pending、挂载、设备身份及扇区重叠；任何冲突均拒绝。
3. **所有写入先过恢复门槛。** 包括 U-Boot 环境、分区表、启动脚本、DTB 和 DATA 迁移。首次布局部署属于独立维护流程，普通 OTA 包不得附带重分区或 U-Boot 本体更新。
4. **未知默认拒绝。** 未知 root、缺少状态、环境 CRC 失败、版本不兼容、无法确认写入范围，都不能默认为另一槽或自动格式化。
5. **保留 last-good。** 候选确认前，失败只能留下无效候选并回到旧系统。系统确认、服务器上报成功、应用 OTA confirmed 是不同状态。
6. **只允许一个升级事务。** 系统 OTA、应用 OTA、原厂 Suricatta 自动安装入口须有统一协调；进程崩溃后的锁释放不能抹去持久化未完成事务。
7. **证据可复现。** 记录源码、配置、镜像哈希、板型、boot_id、单调时间与完整串口日志；公开证据脱敏，原始备份离板保管。

## 3. G1：补齐事实、独立恢复与实施路线

### 输入和工作

- 使用现有 E01–E07 证据建立缺口清单，优先核对 U01–U06。
- 明确板卡硬件版本、启动模式、恢复工具和镜像匹配关系；区分 rootfs 压缩包、分区镜像和完整恢复镜像。
- 查清 U-Boot 本体、环境区、必要 boot0/boot1 和唯一数据的范围。保留 p1 前区域；尾部算术空闲不等于厂商允许使用。
- 对 p1/p3 做完整只读备份与离线分析，核对厂商布局。抽样/签名缺失不足以批准回收。
- 备份应从停写的恢复环境获取一致状态，离板保存、校验，并验证恢复后可启动与业务可用。
- 寻找匹配 S98/modes 的原厂 .swu、sw-description 和打包脚本。不得在板端“试装看写到哪里”。
- 原厂资料持续缺失时作自建路线决策：明确保留区域、自己定义包与映射、现有原厂服务后续处置方式。原厂映射可以保持未知，但自建所有写入范围必须已获证明且不依赖未知区域。

### 交付物

- 板型/版本/存储身份表与精确扇区图。
- 镜像和备份清单：来源、用途、大小、SHA-256、覆盖范围、私有存放位置标识、恢复工具版本。
- 独立恢复启动及恢复后串口/根挂载/ADB/网络/业务报告。
- p1/p3/尾部用途结论，以及“复用原厂”或“自建受控链”的架构决策。
- G0 检查表逐项证据链接；未知项不能勾选。

### 验收与停止条件

只有 [证据文档第 5 节](01-prerequisites-and-evidence.md#5-写入前的恢复放行门槛) 全部满足才通过。不能以文件存在、工具能启动或读取成功代替恢复验证。优先在备用同型板/可替换介质试验；唯一现用板没有可独立验证的恢复路径时，保持写入 BLOCKED，继续主机工作。

## 4. G2：复现 Kernel / Buildroot 基线

### 工作顺序

1. 锁定 U-Boot dirty 构建对应补丁与配置，只审计其能力；不在此阶段升级本体。
2. 获取 Linux 4.9.88 厂商源码、defconfig、实际 .config、DTS、补丁、模块构建参数；固定 Linaro GCC 6.2.1 等工具版本。
3. 保留原始配置，分别复现 zImage、DTB 和匹配模块；核查 vermagic、模块版本、加载路径和固件。
4. 对 Buildroot 候选 commit `37ba456247b4f5a153049c355f77768456de54c2` 记录实际工作树差异、.config、BusyBox 配置、overlay、post-build/post-image、外部工具链和包来源。defconfig 不能代替构建输出目录的实际配置。
5. 将 Xiaozhi genimage 的 20M/1500M/20M 视为候选配置，不输出为“可直接恢复当前板”的整盘镜像。保存 rootfs 镜像与整盘产物的明确类型标记。
6. 清洁输出目录重建至少两次，记录命令、依赖下载哈希和结果差异。若时间戳导致字节差异，解释来源；不得无依据宣称 bit-for-bit 可复现。
7. G1 通过后，先在独立介质或经验证的 RAM/网络启动路径验证基线。具体入口以目标板实测为准，不能假定 SD/TFTP/USB 一定可用。

### 必须保留的初始依赖

| 层次 | 基线保留内容 |
|---|---|
| 启动 | i.MX6ULL clock/pinctrl/串口、MMC/eMMC、分区解析、ext4；无已验证 initramfs 时根设备和根文件系统驱动必须内建 |
| 调试/恢复 | 串口、USB gadget/FunctionFS/ADB 所需配置、必要网络与诊断工具 |

### 验收门槛

- 清洁构建可重复，配置和补丁可追溯；当前板端与候选构建的所有差异有清单。
- 安全启动的基线镜像通过串口启动、根挂载、驱动、ADB/网络、Supervisor/Gateway 与应用 OTA 回归；未执行项目记 NOT RUN。
- 已记录 zImage/DTB/modules/rootfs raw/压缩大小、文件占用、启动耗时、MemAvailable、CMA 和存储余量。
- 若无法证明匹配原板版本，明确标记“新受控基线”，不能冒充原厂镜像复现。

## 5. G3：渐进 Linux 裁剪、容量与布局冻结

### 裁剪在何时进行

**从 G2 完成基线复现后正式开始。** G1 期间可以在主机做依赖和空间分析；不能为尽快腾出 p1 或尾部而直接删当前系统文件。G3 做必要的第一轮缩减，G4/G5 建立升级闭环后再做第二轮优化，并重新执行受影响的 G6 测试。

顺序建议：

1. Buildroot 中不用的示例、图形/多媒体资源、开发文档和测试包先做依赖审计；确认业务及恢复不用后再移除。
2. 精简 applets/脚本依赖。当前 /bin/sh=bash，先审计 S98 等脚本，再决定保留 bash 或迁移为 POSIX；不能仅删 bash 改链接。
3. Kernel 每次只裁一个主题，保留原配置与 diff；重新构建 Kernel/DTB/模块成套产物并回归。
4. CMA 先查 DTS/reserved-memory、内核配置、cmdline 和 DMA 消费者。320 MiB 只是审计起点；缩减值由峰值需求与压力测试确定。
5. 区分生产和调试镜像；生产镜像也应保留可恢复、可诊断能力。首次不将只读根、overlay、新 init 和大规模裁剪同时引入。

当前 S99 会修改 /etc/inittab，rootfs 若改只读必须重新设计持久化/启动条目并单独测试；不能把“可只读挂载”当作现有 Supervisor 无需调整。

### 槽位容量的统一口径

设：
- C_A/C_B：批准槽位的可写字节范围；
- I：解压、展开稀疏格式后实际写入的镜像地址范围；
- F：文件系统声明总容量；
- U：完整装入 Kernel/DTB/modules/rootfs 后文件系统已用容量；
- R：经评审冻结的运行余量、保留块和增长预算。

最低判据：

```text
I <= min(C_A, C_B)
F <= 对应槽位范围
U + R <= F
所有写入区间与保留区/活动槽/last-good 不相交
```

如 Kernel/DTB 已包含在 rootfs 的 /boot，不能在槽位预算里重复计数；若独立 BOOT_A/B，则分别计算。压缩 .swu 长度、du、df、raw 文件长度和 ext4 声明容量必须分别列出。

当前约束：

- p1=1,048,576,000 bytes；p2=1,572,864,000 bytes；p3=524,288,000 bytes，但 p1/p3 尚不可用。
- 若将来批准 p1/p2 为不对称槽位，通用镜像必须适配最小的 1,000 MiB 槽。不能将现有 1,500 MiB raw 镜像截断；应从构建产物重新生成合适大小的文件系统。
- p3 后 761,265,152 bytes（约 726.97 MiB）仅为算术尾部；用途未确认且当前文件占用已接近，不能作为默认 B 槽。
- DATA 要独立预算：当前及回退应用 releases、持久状态、配置、日志上限、下载包、解压/校验临时空间及故障重试余量。p3 的 500 MiB 不能未经实测认定足够。
- /tmp 是 tmpfs，不能承担跨重启包/状态；也不能默认约 489 MiB 可见内存足以解压整包。
- 建议初始容量评审使用不少于 20% 文件系统可用增长余量作为候选指标；最终以实测和产品约束冻结。该比例是规划值，不是已有性能或容量结论。

### 布局决策

优先评审“每个 rootfs 槽自带 /boot 的 Kernel/DTB，独立 DATA”的较少分区方案；与现有加载方式相近但仍须验证 U-Boot 对新镜像 ext4 features 的读取兼容性。禁止凭 ext4load 命令存在认为所有 mkfs 默认特性兼容。

若需重分区，单独形成首次迁移方案：保护范围、备份、停机、独立恢复、每步验证及中断恢复；普通 OTA 不承担迁移。不能在运行中的 p2 上在线缩容。既有 p1/p2/p3 与 A/B/DATA 的正式映射仅在 G1 用途证明与本阶段预算通过后填写。

### 验收门槛

每次裁剪有可撤销配置差异、前后指标和必要功能回归。两槽 raw/FS 尺寸、增长余量、DATA/暂存预算、ext4 features 与 U-Boot 读取均通过；构建阶段拒绝超限产物。若容量不足，应调整镜像/布局或保持 BLOCKED，不能压缩包“看起来够小”就放行。

## 6. G4：启动槽位、bootcount 后端与掉电安全

### 先验证现有 U-Boot 能力

必须从匹配 2017.03 厂商源码/配置确认实际启动计数逻辑、后端、环境布局和复位语义。缺少 bootcount 交互命令不等于无计数；设置 bootlimit 变量也不等于启动代码会使用它。

| 候选实现 | 必须证明 | 无法证明时 |
|---|---|---|
| 已编译的 bootcount 后端 | 存储位置、更新点、冷启动/复位/物理断电保持行为、错误返回、bootlimit 判定边界 | 不作为可靠重试计数 |
| 环境脚本实现计数 | 脚本所有启动路径执行；持久化失败可检测；环境副本/写序/CRC 和磨损可接受 | 不以多次 saveenv 拼出事务 |
| 独立冗余启动状态 | 区域用途、U-Boot 与 Linux 两端支持、格式、原子性、恢复读取规则 | 不占用未知“空闲扇区” |
| 只有 RAM/保持寄存器计数 | 区分热复位与彻底断电，验证丢计数风险 | 不能冒充冷启动可靠后端 |

**范围冲突处理：** 若现有 U-Boot 无法读取可靠状态或无法执行回退，G4 阻塞。不能仅靠 Linux 添加 bootcount 文件解决，也不能悄悄重编刷写 U-Boot。本轮“不升级 U-Boot 本体”约束下，需提出单独范围变更与恢复方案，或明确只能完成非自动回滚原型。

### 启动状态定义与不变量

建议逻辑字段：format_version、sequence、confirmed/last_good_slot、pending_slot、attempts、attempt_limit、候选版本/哈希、结果码、CRC。字段名可以随实现变化，语义须冻结。

- active 是本次实际运行槽，必须能与 root、Kernel/DTB 来源和持久状态核对，不能只信旧环境值。
- 初始 confirmed/last_good 为已验证旧槽，pending 为空。
- writer 只有在候选完整写入、flush、回读成功后，才持久化 pending。
- U-Boot **进入候选 Kernel 前**持久化消耗一次尝试。若计数不能落盘，不启动候选；否则死在早期内核时可能永远不计数。
- 建议初始候选尝试上限 N=3（设计值）。精确定义“最多启动候选 N 次”，测试 N-1、N、N+1 边界，避免 bootlimit 比较语义产生额外一次尝试。
- Kernel/DTB 加载失败优先在同次启动内回退旧槽；启动后卡死由已验证 watchdog/复位策略返回 U-Boot。普通用户态脚本不能处理内核卡死。
- 只有可信健康确认器完成全部必需项后才把候选设为 last-good 并清 pending；确认与计数清零是同一逻辑事务。
- 回退也要记录故障结果；旧槽启动失败应进入经过验证的恢复策略，不能无穷循环。
- 元数据全部损坏时只使用独立可信的已验证恢复策略；不能猜测新槽有效。首次迁移阶段可将受保护 p2 定为恢复对象，但后续槽位轮换必须重新定义可信 fallback。

### 冗余与持久化协议

对现有环境冗余或新双记录方案，均需说明实际介质与实现，不把“CRC+两份”当作已完成：

1. 旧有效记录保持不动，写另一副本的完整状态、序号和 CRC。
2. 检查写入返回值、缓存刷新和设备持久化要求，回读验证后才允许后续动作。
3. 启动时按格式/CRC/序号/副本有效标记选择合法记录；定义同序号冲突、序号回绕和双无效情况。
4. 两副本不能因一次覆盖/擦除动作同时失效；布局、写粒度、eMMC 缓存与电源故障行为必须以实际测试约束。
5. CRC 仅用于损坏检测，不代替签名和访问控制；普通 rename/sync 不自动等价于 eMMC 掉电原子性。
6. 减少持久写入频率：计数主要针对 pending 尝试；避免正常每次启动都重写环境导致不必要磨损。
7. 清楚区分 boot attempt 计数与 SWUpdate transaction marker；两者必须有集成协议，不能互相替代。

### 验收门槛

- 两槽的 Kernel/DTB/root 始终一致，不出现 A Kernel+B RootFS 混搭。
- 冷启动、软件重启、看门狗复位、候选 Kernel/DTB 损坏、root 挂载失败均可在 N 次内回旧槽。
- pending/计数/确认写入各中断点均保留可用记录或进入明确恢复路径。
- 证明 watchdog 在早期启动失败场景仍有效；若只在用户态启用，早期挂死自动回退不得判 PASS。
- 全程保留旧槽；新系统通过后才允许进入正式槽轮转。

## 7. G5：SWUpdate 包、写入闭环、健康确认与应用共存

### 包与 writer

优先复用匹配版本 SWUpdate 的实际 handler 和验签能力，不凭新版本文档假定 2019.11.0 已支持某选项。需要核实厂商补丁与构建配置。

每个包至少包含受签名保护的板型/硬件版本、布局版本、系统版本、最低 bootloader 能力、payload 类型/展开长度/哈希、Kernel/DTB/模块/rootfs 版本关系、DATA schema 兼容范围。若存在 sw-description 外的 manifest，二者必须绑定到同一受信内容，避免目标/长度不一致。

- 在任何目标写入前完成身份、签名、完整性、兼容性和容量检查；签名失败、缺签名、错误公钥和篡改均必须拒绝。
- 流式 handler 可能在完整 payload 哈希得出前开始写：只有明确限制为无效的非活动槽、且失败不设置 pending 的设计才可评审；首次实现优先使用持久暂存并预验证。
- 审计所有 pre/post scripts、bootenv 和 handlers。受签包中的脚本也可能越界；首次实现采用最小白名单，禁止任意块设备、整盘和 U-Boot 本体操作。
- 写目标前再次核对实际设备身份/边界/挂载和当前运行槽，排除 TOCTOU；非活动槽若仍挂载或被占用则拒绝。
- 写入出错、ENOSPC、只读、短写、校验失败一律结束事务，不设置 pending，不清 last-good。
- 成功后 flush、回读目标有效范围、校验内核/DTB/rootfs 关联，再提交 pending。部分写入候选永不参与启动。
- 测试 p2 当前活动、未来 last-good、设备路径别名和整盘重叠四类拒绝，不能只比较字符串。

上游 SWUpdate 2019.11 的安装器存在脚本和 bootloader environment 更新路径；这仅提供离线审计入口，不能证明厂商板端配置相同：[2019.11 installer.c](https://github.com/sbabic/swupdate/blob/2019.11/corelib/installer.c)。

### 状态机与服务器确认

```text
IDLE → PACKAGE_VERIFIED → WRITING_INACTIVE → SLOT_VERIFIED
     → PENDING_BOOT → BOOTING_CANDIDATE → HEALTH_CHECK → CONFIRMED

下载/验签/写入失败 → 保持旧槽，候选无效，记录 FAILED
候选启动/健康失败 → 尝试耗尽或显式失败 → ROLLED_BACK
确认写入中断 → 按 G4 有效状态恢复，禁止凭 /update-ok 猜成功
```

Suricatta/hawkBit 的 SUCCESS 只能在本地 confirmed 持久提交之后上报；网络上报失败需可重试且幂等，不反向破坏本地确认。旧包 postupdate.sh 不得移植；板端当前 /update-ok 的历史行为也不能当作新方案的健康确认。

### 分层健康门槛

| 层级 | 必需检查 | 判定要求 |
|---|---|---|
| 启动身份 | 当前 root、slot ID、版本/哈希、Kernel/DTB/模块一致 | 与 pending 候选完全匹配；未知不确认 |
| 存储 | RootFS 与 DATA 正确挂载，状态存储可持久写/读，无必须处理的 I/O 错误 | DATA 缺失不得落到 root 上创建同名空目录掩盖故障 |
| 驱动 | 板型必需 GPIO、I²C/AP3216C、串口和网络设备 | 具体探针按实际产品配置冻结，必需项不得静默跳过 |
| 监督 | Supervisor IPC 真正可连接、PID/身份正确、init respawn 生效 | socket 文件存在和脚本 exit=0 都不足够 |
| 业务 | Gateway 正在运行，Agent/IPC、L1 就绪和本地可控 L2 业务链通过 | 不能仅凭 ROLLED_BACK/CONFIRMED 文本或进程名 |
| 稳定性 | 持续观察，无反复崩溃/重启，资源未耗尽 | 通过窗口内的连续成功而非瞬时探针 |

建议首轮参数：单调时钟总期限 120 秒、连续健康观察 30 秒、候选上限 N=3；均须在 G2 实测启动时间后冻结并留余量。外部云服务器短时不可达单独记为 degraded，不应独立触发系统回退；用本地受控业务链区分本机故障与外网故障。真实串口和真实云平台未测时仍明确限制。

健康进程挂死、被杀或未启动都不能自动成功；超过期限要由可验证的独立 watchdog/复位策略触发失败处理。确认写入者权限受限，并校验本次 boot_id/候选版本，防止旧进程延迟回调确认错误槽。

### DATA 与 Supervisor 集成

- 现有 /opt/smartgateway 不等于独立 DATA，迁移需要 G1 备份和明确方案。DATA 必须先挂载，再启动依赖服务。
- 保留应用 releases/current、配置、事务状态和日志；新系统不能对共享状态做旧系统不可读的单向改写。
- 应用和系统 OTA 使用一个全局互斥协议，各自状态独立。候选未确认期间阻止新的应用升级，以便归因和回滚。
- 进程锁只处理并发，持久事务日志处理跨重启恢复；检测到旧事务不能简单删锁后继续。
- 验证 S99 stop 后确实稳定停止、start 后恢复 respawn，以及升级/回滚后的业务实际运行；不要继承测试工具“验证后停服务”的结束状态。
- 原厂自动升级入口和自建入口的启停/接管属于后续受控部署内容，本次文档提交不触碰运行中的 S98。

### 验收门槛

在有恢复条件的测试布局完成 A→B、B→A 正常升级，以及所有拒绝路径。错误包不得写任何目标；写失败不得 pending；确认必须有系统和业务证据；回退后旧系统与共享 DATA 业务仍可用。G5 功能通过后仍需 G6 真断电测试才能声称可靠 A/B。

## 8. G6：故障矩阵、Linux 裁剪回归与交付

### 故障矩阵

以下每项记录触发方法、实际命中阶段、串口/状态/分区哈希、预期和实测；NOT RUN 不能当 PASS。

| 场景 | 必需结果 |
|---|---|
| 缺签名、错签名、错误哈希/板型/布局版本、截断包 | 写前拒绝，活动槽及启动状态不变 |
| 超出最小槽、磁盘/暂存不足、解压超限 | 不越界；不误用 /tmp；不 pending |
| 当前槽、last-good、p2 保护范围、设备别名/整盘重叠目标 | 全部拒绝，无保护区写入 |
| 写入前/中/后断电，读回失败，短写或 I/O 失败 | 旧槽仍启动，候选不被选中，事务可解释 |
| pending 提交中断 | 选择旧有效记录或完整新记录，绝不启动半写槽 |
| bootcount 更新中断、冷启动丢电、N 次边界 | 有限候选尝试，不无限循环，不重复重置计数逃避上限 |
| Kernel/DTB 损坏、不匹配、RootFS 不可挂载 | 回到 last-good，串口能解释原因 |
| Kernel 早期挂死、watchdog 复位 | 未依赖 Linux 健康进程也能形成回退闭环 |
| DATA 未挂载/只读、配置不兼容 | 不假确认，不破坏旧 schema；回退后可恢复业务 |
| Supervisor IPC 失败、Gateway/Agent 异常、健康进程被杀/卡死 | 不确认；有界失败；旧槽业务可用 |
| 外网中断但本地系统/业务正常 | 按既定 degraded 策略处理，不引发无意义切槽循环 |
| confirmed 提交中断、上报 SUCCESS 失败 | 本地状态自洽，上报可重试，不把半提交当成功 |
| 系统/应用/原厂 OTA 并发、跨启动旧锁或旧事务 | 单 writer；拒绝新事务或明确恢复，不并行写 |
| 重复版本/旧包重放、旧健康结果延迟到达 | 按版本/候选身份策略拒绝或幂等，不错误确认 |
| 两个启动元数据副本损坏 | 进入已验证的恢复路径；不随意启动未知槽 |
| 裁剪后缺模块/固件/applet、bash 被替换、CMA 峰值压力 | 必需功能全回归；无静默降级或内存分配失败 |

### 真实掉电方法与覆盖

区分三类记录：软件 reboot、硬件 reset/watchdog、切断板卡供电。受控 reboot 尤其是预先 sync 后 reboot，不替代物理切电。

在已具备恢复条件的板/介质上，用受控电源或等价装置触发真实切电，确保不是仅断 ADB/串口而板卡仍由其他接口供电；记录电源切断与阶段触发证据。测试切电前不得额外 sync 来规避目标缓存窗口。每轮确认设备完全掉电再恢复，记录时序和残留状态。

建议首轮最低覆盖：每个关键持久化窗口（写槽、pending、计数、确认）至少 10 次实际切电，覆盖早/中/晚和随机位置；正常双向升级至少各 3 次；错误包与保护拒绝项逐项执行。次数是工程验收起点，不是统计可靠性保证；有一次未解释状态、损坏 last-good 或无限循环即 FAIL，修复后重测受影响矩阵。

### 裁剪回归指标

- 同一硬件、相同负载记录裁剪前后 zImage、DTB、modules、RootFS raw/压缩/已用大小。
- 记录启动时间、MemAvailable、CMA/DMA 峰值、业务吞吐/延迟和存储增长；明确取样方法及次数。
- GPIO/IRQ、I²C/AP3216C、WiFi/以太网、真实串口、ADB、Gateway、Supervisor、应用 OTA、系统 OTA 都按产品必需项执行。
- 不以“减少 10%/15%”作为替代功能正确性的硬指标；尺寸目标以 G3 预算为准。
- 暂不覆盖的真实云平台、存储硬件故障等明确列为限制，若属产品必需则阻止发布。

### 最终交付与门槛

- [ ] G1–G5 每个入口/出口均有证据，G0 不再存在未关闭阻断项。
- [ ] 系统双向升级、N 次内回退、确认写入、真实切电和保护 p2/last-good 全部通过。
- [ ] 回滚后不只“能启动”，还确认旧系统、共享数据和业务可用。
- [ ] 源码 commit、配置差异、构建清单、包版本/哈希、签名验证和公钥轮换策略可追溯；私钥不入仓库。
- [ ] 恢复文档由独立于当前根分区的路径实际执行过，包含元数据损坏时步骤。
