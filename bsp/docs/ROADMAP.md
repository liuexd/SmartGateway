# SmartGateway-BSP i.MX6ULL 路线图（D16 后调整版）

> 分支：`feature/bsp-imx6ull`  
> 规划基线：42 天 / 6 周；当前已推进到 D16。  
> 本版调整：**先完成应用级 OTA，再将 RS485/Modbus RTU 作为最后一个新增外设模块**。  
> 原则：计划不等于完成；仅凭实际测试证据标记 PASS。存储恢复条件未核实前，不刷写 U-Boot、Kernel、DTB 或 rootfs。

## 2. 为什么 OTA 在前、RS485 在后

1. 当前 Gateway 已有 WiFi/TCP 数据链路，可先实现升级包校验、版本切换、健康确认和失败恢复。
2. 应用级 OTA 不依赖 RS485 外设先完成。
3. RS485 留作最后一个新增外设模块，用于综合验证 UART/pinmux、串行通信、Modbus RTU、CRC16、超时和节点集成。
4. 本次 OTA 仅升级 Linux 用户态 SmartGateway 应用，不升级 U-Boot、Kernel、DTB 或覆盖 rootfs。A/B 系统 OTA 是扩展目标，需另行验证分区和恢复机制。

## 3. D17–D25：应用级 OTA

### D17：升级前置条件和安全边界
- 只读核查 `findmnt`、`mount`、`df -h`、`/proc/mounts`，确认真实 rootfs、候选安装目录所在文件系统及剩余空间。
- 实测安装目录是否可写、重启后文件是否保留；不能仅凭路径名假定 `/opt` 一定持久。
- 核对当前 Gateway 的启动、停止、重启机制。Buildroot 系统不假定一定使用 systemd。
- 确认当前版本的备份与恢复办法；不写块设备。
- **验收**：形成存储布局、运行方式和恢复条件记录。安装位置未确认前不执行升级。

### D18：升级包格式与版本状态机
- 定义 manifest：版本号、目标架构（ARM EABI hard-float）、文件大小、SHA-256、文件列表和兼容性字段。
- 定义状态：`DOWNLOADED → VERIFIED → STAGED → ACTIVATED → HEALTHY → CONFIRMED`。
- 持久化已确认版本、候选版本、升级状态和失败原因。
- **验收**：manifest 解析测试通过；非法字段、错误版本和错误架构被拒绝。

### D19：升级包传输与完整性检查
- 在主机端构建可重复的测试包，验证长度、SHA-256、文件截断和内容损坏。
- 先验证暂存区写入与失败清理，再接入选定的网络传输路径；不能直接覆盖正在运行的二进制。
- SHA-256 检测意外损坏；若要防止恶意替换，还需要签名验证与可信公钥，不能把裸 checksum 当作身份认证。
- **验收**：合法包通过；截断、哈希错误、错误架构包均拒绝，当前版本不变。

### D20：解包与候选版本目录
- 在确认可写、空间足够的文件系统中建立 staging 和按版本隔离的 release 目录。
- 拒绝绝对路径、`..` 路径穿越和越界符号链接。
- 解包到候选目录，检查权限、ELF 架构和版本信息。
- **验收**：失败不会修改当前运行版本。

### D21：原子版本切换
- 仅在候选 release 与 `current` 位于同一文件系统时，使用临时符号链接加 `rename()` 原子切换。
- 检查系统调用返回值；按设计对关键目录更新执行 `fsync()`。
- **验收**：切换前后 `current` 指向预期版本；失败时旧版本仍可用。

### D22：重启与健康检查
- 通过设备真实的启动/进程管理方式启动候选版本。
- 检查进程存活、版本号、必要设备访问和 Gateway 基础通信。
- 只有健康检查通过才进入 HEALTHY，确认步骤成功后才进入 CONFIRMED。
- **验收**：版本确认有日志和持久化状态；不能只凭 exec 或 send 返回成功宣布 OTA 完成。

### D23：失败回滚与重启恢复
- 候选版本启动失败或健康检查超时，停止候选版本并恢复最后一个已确认版本。
- 重启时读取持久化状态；未 CONFIRMED 的候选版本不得覆盖已确认版本。
- 保留当前已确认版本，最多清理更旧的非活动版本；删除前确认没有进程仍在使用。
- **验收**：失败后回到旧版本；重启后状态可解释；`current` 不指向不存在的目录。

### D24：故障注入与回归
- 测试包损坏、下载中断、磁盘空间不足、解包失败、错误架构、启动失败、健康检查失败、切换失败和重启后待确认状态。
- 确认失败路径可观测、临时文件可清理、旧版本未被提前覆盖。
- 对 Gateway 消息队列、Sensor Agent、设备注册和北向 TCP 做升级前后回归。

### D25：端到端验收与文档
- 跑通升级包生成、传输、校验、staging、切换、重启、健康确认及失败回滚。
- 记录命令、日志、版本号、SHA-256、故障注入结果和已知限制。
- **验收**：发布 D17–D25 实测记录；只有板端实际通过的场景才标记 PASS。

## 4. D26–D34：RS485 / Modbus RTU（最后新增外设）

### D26：UART、pinmux 与硬件核对
- 确认板卡可用 UART、设备树 pinmux、设备节点、串口参数、RS485 收发器型号和电气连接。
- 检查是否与 console、WiFi 或其他外设复用冲突的引脚。
- 核对 A/B、GND、电平和方向控制要求；断电接线，不能把 RS485 A/B 当作 TTL UART。
- **验收**：保存 UART 资源表、接线图和只读核查结果。

### D27：UART 基础收发
- 最小化验证串口收发、波特率、数据位、校验位、停止位和超时。
- 明确硬件自动方向控制或 GPIO DE/RE 方案，验证发送完成后释放总线。
- **验收**：收发日志可复现；先不混入 Modbus 业务逻辑。

### D28：Modbus RTU 帧与 CRC16
- 独立实现帧编码/解析，定义从站地址、功能码、寄存器范围和字节序。
- 用已知测试向量验证 CRC16/Modbus 及 CRC 字节顺序。
- **验收**：正确帧通过；CRC 错误、非法长度、地址和功能码被拒绝。

### D29：超时、部分帧与异常恢复
- 处理半帧、多帧合并、帧间静默、响应超时和非法响应。
- 设置有限重试与退避，不能无限重试或阻塞 Gateway 主循环。
- **验收**：无响应和 CRC 错误时，采集线程仍能退出，状态与错误计数正确。

### D30：NODE05 Modbus Agent
- 新增独立采集 Agent（计划名 `sgw-modbus-agent`），将寄存器数据映射到现有 DATA 消息。
- 复用节点 ID、序号、消息队列和北向转发设计。
- **验收**：串口采集数据生成标准 NODE05 消息。

### D31：Gateway 节点接入
- 为 NODE05 / Modbus 增加设备类型和所需状态字段。
- 保持“节点在线”和“采集成功”语义分离；通信错误不能伪装成有效采样。
- **验收**：NODE04 与 NODE05 并行运行，互不覆盖状态。

### D32：多节点并发回归
- 同时运行 GPIO 事件、NODE04 Sensor Agent、NODE05 Modbus Agent 和 Server Link Worker。
- 检查队列满、Server 断线、Agent 退出、设备无响应和状态更新。
- **验收**：已有单元测试与新增 Modbus 测试通过。

### D33：RS485 故障注入
- 测试 CRC 错误、从站无响应、错地址、超时、短帧和方向控制异常。
- 核查资源释放、日志限频、错误计数和恢复能力。
- **验收**：故障可观测、重试有界，恢复后继续采集且不污染旧数据。

### D34：RS485 阶段验收
- 归档 UART/RS485 资源、Modbus 帧、CRC 测试、Agent 接入和板端验收。
- **验收**：RS485 成为最后一个新增外设，NODE04 与 NODE05 集成回归通过。

## 6. OTA 安全边界

- **先核查存储，再写入**：当前基线记录 rootfs 为 `/dev/mmcblk1p2`、ext4，但安装目录是否可写、重启持久性、空间和真实分区布局仍需 D17 实测。
- **不升级 bootloader/kernel/rootfs**：必做范围仅用户态应用。A/B 系统 OTA、U-Boot 环境修改、块设备写入和覆盖 DTB/Kernel 不在本计划。
- **完整性不等于真实性**：SHA-256 检测损坏；防止攻击者替换包需要签名验证和可信公钥。
- **保留已确认版本**：候选版本健康确认前，最后一个已确认版本不得清理或覆盖。
- **原子切换有前提**：链接和目标必须位于同一文件系统；检查 rename、目录持久化和重启恢复状态。
- **不假定 systemd**：依据 Buildroot 当前实际 init/启动脚本设计进程管理。
- **不声称 exactly-once**：下载完成、校验通过、进程启动和业务健康确认是不同层级的状态。

## 7. 每阶段交付规则

1. 运行单元测试与交叉编译。
2. 在开发板验证最小功能。
3. 测试至少一个失败场景。
4. 保存命令、实测输出、验收结果与限制。
5. 检查 `git diff --check`、`git status` 后再提交；每个提交只聚焦一个主题。
6. 计划内容不等于完成状态；只有实测证据支持才标记 PASS。

本路线图调整了 OTA 与 RS485 的先后，但不追认尚未完成的恢复核验、Server 端接收确认或未执行的故障测试。
